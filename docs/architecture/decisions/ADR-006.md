# ADR-006: Keep Database Integrity Guards Alongside Service Workflow Decisions

## Status

Accepted — 2026-10-11.

## Context

The original transcript and its speaker labels must remain unchanged after creation (FR-028).
Refusing updates and deletes alone leaves two ways to change a committed original: append new
content or move existing content into it. Workspace ownership, default folders, restricted
recipients and cross-workspace relationships must also remain consistent at transaction end.
Several of these rules cannot be expressed with a CHECK, foreign key or unique index alone.

[ADR-003](ADR-003.md) puts meeting-content authorization in Access Policy and rejects row-level
security as the authorization mechanism. It does not replace stored-data integrity checks.
[ADR-005](ADR-005.md) requires actor-attributed audit events in the same transaction as a change.

### Functional Pressures

- **Original transcript preservation (FR-028):** editing transcript text or speaker labels must
  retain the original unchanged. Guards must refuse later appends and reparenting as well as
  updates and independent deletes.
- **Workspace and membership consistency (FR-005, FR-006, FR-007, FR-037):** a workspace starts
  with its Owner and default folder; personal workspaces cannot receive invitations; the Owner
  cannot be removed or re-roled. Restricted access belongs to selected workspace members, and
  removing the last recipient requires explicit replacement without automatic access expansion.
- **Folder preservation and workspace boundaries (FR-034, FR-035):** deleting a nondefault
  folder moves its meetings to the default folder without deleting them. The default folder
  cannot be deleted while its workspace exists, and meetings can move only between folders in
  the same workspace.
- **Intentional deletion (FR-008, FR-036):** authorized workspace and meeting deletion removes
  their contained transcripts and notes. Original-content guards must allow these cascades;
  services remain responsible for authorization and recording cleanup.

### Non-Functional Pressures

- **Integrity (NFR-011):** edited transcripts must be identified as edited, and the original
  must remain retrievable. The transaction seal protects the original stored content; services
  and presentation paths remain responsible for version selection and the edited marker.
- **Accountability (NFR-010):** covered changes need actor-attributed audit records with the
  action, target and timestamp, without meeting content. Services write them in the same
  transaction as the change. Audit records outlive deleted targets, and the application role's
  grants prevent modifying existing events.
- **Confidentiality (NFR-007, NFR-009):** every content path must enforce meeting permissions.
  Database guards support consistent membership and grant relationships, while Access Policy
  and services enforce authorization; integrity guards alone do not satisfy these requirements.
- **Time behaviour (NFR-001):** workspace, folder and meeting pages must load in under two
  seconds for at least 90% of requests. Plain permission reads avoid unnecessary serialization;
  exclusive locks are reserved for workflows that need them. Meeting the target still requires
  measurement under representative load.

## Decision

Services enforce the applicable authorization rules, choose workflow steps, return useful errors
and write audit events.
PostgreSQL retains declarative constraints, audit-role grants and narrow integrity guards that
refuse violations of the invariants they enforce. Triggers must not grant access, choose
replacement recipients, move meetings or generate actor-attributed audit events.

- Keep the deferred guards for exactly one workspace Owner and one default folder, a valid
  original transcript, and grants consistent with workspace membership and restricted access.
  Exactly one Owner does not ensure that the same member remains Owner: Accounts & Workspaces
  must refuse removal or re-roling of the Owner (FR-007) and deletion of a personal workspace
  (FR-008). Guards do not replace those service checks.
- Keep guards against cross-workspace folder and meeting moves and invitations into personal
  workspaces. Services enforce the applicable authorization rules before performing workflows.
  Meeting-content access remains governed by Access Policy under [ADR-003](ADR-003.md);
  workspace-administration permissions remain in Accounts & Workspaces.
- Stamp `transcript_revision.initialization_xid` with the top-level PostgreSQL transaction ID.
  Initial original speakers and segments may be inserted or moved into the original only in
  that transaction, including through savepoints. Later appends and reparenting are refused.
  Updates, independent deletes and edited-to-original relabelling are also refused. Cascading
  deletion through the containing meeting or workspace remains allowed.
- Folder deletion explicitly locks the workspace and acting membership, then the source and
  default folders. The service moves meetings, writes one `meeting_moved` event per meeting,
  and deletes the empty source folder in one transaction. `guard_folder_deletion` only refuses
  deleting the default folder or an occupied folder while its workspace exists.
- Ordinary membership permission lookups remain plain reads. The deletion path uses
  `lock_role()` and retains workspace `FOR UPDATE` before folder locks, matching the deletion
  guard and avoiding a later lock upgrade between concurrent folder deletions.

Removing the last selected recipient requires explicit selection of another remaining workspace
member before removal (FR-007). Services implement this workflow and enforce its authorization;
database guards prevent a restricted meeting from having no recipients. Removal must not
automatically grant the Owner access or unrestrict the meeting.

## Consequences

- Violations of database-enforced invariants are refused even when a future repository omits
  the corresponding check. Authorization, Owner immutability, personal-workspace deletion
  restrictions and complete audit emission still depend on service implementation and tests.
- Original-transcript provenance survives later transactions without retaining deleted content.
- Multi-row workflows may construct a valid state atomically before deferred checks run.
- PostgreSQL transaction IDs and trigger SQL are implementation dependencies, so tests must use
  PostgreSQL and cover appends, reparenting, savepoints, cascades and rollback.
- Services still need explicit checks and error translation; an integrity exception is a final
  safeguard, not the normal API decision path. Guards require documented lock ordering and
  concurrency tests. New workflow decisions belong in services rather than additional triggers.

## Alternatives Considered

- Service checks alone leave stored-data integrity dependent on every writer following them.
- UPDATE/DELETE protection without a transaction seal permits appends to a committed original.
- Database authorization or workflow triggers would hide workflow decisions. Trigger-based
  auditing would require application-supplied actor and intent context; stored row changes alone
  do not identify the intended event. ADR-005 instead assigns explicit event emission to the
  module performing the change, through Audit's interface in the same transaction.
