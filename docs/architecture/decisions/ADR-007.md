# ADR-007: Serve the Notes LLM with Ollama Through Its Native API

## Status

Accepted — 2026-10-19.

## Context

[ADR-004](ADR-004.md) makes a built-in model the default writer of notes, served by `llm-runtime`
on the GPU host ([ADR-002](ADR-002.md)), and names an OpenAI-compatible server such as llama.cpp
server or vLLM as the runtime. The notes worker already calls Claude through the Anthropic API.
It now needs a self-hosted runtime it can call, and a way to run that runtime in Compose.

### Functional Pressures

- **Built-in notes without egress (FR-022):** with no external provider, notes are written by a
  model inside the deployment and no transcript leaves it.
- **Whole transcripts or a clear failure (FR-018, FR-019):** a transcript that does not fit the
  model's context window must fail as too long, or later be split into chunks. A runtime that
  silently drops part of the prompt produces notes that look complete but miss part of the meeting.
- **Ukrainian and mixed speech:** the model must write notes in Ukrainian with the preset's
  headings. Which open model does this best on the reference GPU is not yet measured.

### Non-Functional Pressures

- **Shared GPU (NFR-002):** the reference GPU host has a 12 GB GPU that the ASR worker shares, and
  transcription has a turnaround target. The language model must fit beside it, or leave the GPU
  when idle.
- **Fault tolerance (NFR-015):** a runtime that is down or out of memory must fail notes jobs as
  retryable, not stop the worker or the web.
- **Self-hosting (NFR-016, NFR-017):** an operator must be able to start the runtime and fetch a
  model with the project's own Compose file, without building or converting model weights.

## Decision

Run Ollama as `llm-runtime` and call its native `/api/chat` endpoint.

- **Runtime in Compose.** `compose.yaml` runs `ollama/ollama`, pinned by version tag, as
  `llm-runtime` under the `gpu` profile, with an NVIDIA GPU reservation, its models in the
  `llm-models` volume and its port published on `127.0.0.1`, or on the GPU host's
  private-network address in the two-host layout. `OLLAMA_NUM_PARALLEL=1` makes it
  answer one request at a time. A one-shot `llm-pull` service pulls the configured model, and
  `task llm:up` starts the runtime and waits for the pull.
- **Native API.** The notes worker posts to `/api/chat` with httpx2 (`workers/notes/ollama.py`).
  Each request sets `num_ctx`, `num_predict` and `keep_alive`, turns thinking off, and sends
  `truncate: false` and `shift: false`. By default Ollama cuts a prompt longer than `num_ctx` and
  shifts the context while answering, and both silently drop transcript. With both off, a prompt
  over the window is refused and an answer that runs out of it stops, and the worker reports either
  as `transcript_too_long`. Notes written this way carry the provider `whadio` and the model tag
  Ollama reports.
- **The model is a deployment setting.** `WHADIO_NOTES__LLM__MODEL` names the Ollama tag; the
  worker and `llm-pull` read the same variable. The first candidate is `gemma4:12b-it-qat`, Gemma 4
  12B with quantization-aware 4-bit weights: a 7.2 GB download (7.0 GB of weights and a 0.2 GB
  vision projector). Five of every six layers use a 1,024-token sliding window and the others one
  key-value head, so a 32,768-token window needs an estimated 1 GB of cache, and the loaded model
  about 9 GB. It is confirmed only by a benchmark against `gemma3:12b` and `qwen3:8b` on the same
  Ukrainian recording: whether the notes parse, whether their headings and language are right, the
  memory used and the time taken.
- **Anthropic stays the default provider** until that benchmark picks a model; the operator
  switches with `WHADIO_NOTES__LLM__PROVIDER=ollama`.

### Deviation from ADR-004, the high-level design and the threat model

[ADR-004](ADR-004.md) lets each workspace Owner configure a provider and key; its consequences, the
job-delivery paragraph of the [high-level design](../high-level-design.md#5-interfaces) and
[threat model](../threat-model.md) risk R-14 have the Owner's key travel to the notes worker inside
the `NotesRequested` message. Until per-workspace provider configuration is built, which comes after
the MVP, this is not so:

- `NotesRequested` carries no provider and no key. The provider, the model and the Anthropic key are
  settings of the notes worker's deployment (`notes.llm`), one for every workspace.
- The key is therefore the operator's, read from the environment, and never enters the broker. R-14's
  mitigation for keys in payloads does not apply yet; the key's exposure is that of the worker's
  environment.
- With the default settings, notes are written by Anthropic, so transcripts leave the deployment
  without an Owner's choice, contrary to FR-022 and ADR-004's local default. Choosing the Ollama
  provider restores it. The default changes once the benchmark above confirms a model.

ADR-004, the high-level design and R-14 stay as the target. Per-workspace providers will put the
provider, and the key in encrypted form, into the job message as they describe.

## Consequences

- ✅ A transcript that does not fit the window fails as too long instead of producing notes from
  part of it.
- ✅ A self-hosting operator runs the model with `task llm:up` and one setting; Ollama fetches
  quantized models from its library, so no weights are built or converted.
- ✅ Changing the model is a change of `.env`, which the benchmark needs.
- ⚠️ The GPU is shared with the ASR worker. The worker should take one notes job at a time
  (`WHADIO_NOTES__CONCURRENCY=1`): with `OLLAMA_NUM_PARALLEL=1` further requests wait inside Ollama,
  and the wait counts against the job's timeout. `keep_alive` unloads an idle model after five
  minutes, so the ASR worker gets the memory back; while the model stays loaded, transcription has
  about 3 GB left. When the model does not fit, Ollama keeps some layers on the CPU, and notes slow
  down rather than fail.
- ⚠️ A tag is not a content pin: pulling the same tag again can fetch a newer build. The benchmark
  records the model digest from `ollama list`.
- ⚠️ The worker is bound to Ollama's own API and its error wording: Ollama tells a prompt over the
  window apart from other refusals only by the word "context" in its message. Another server would
  need its own chat model class.
- ⚠️ The Compose notes worker does not wait for the runtime: `task workers:up` enables the `gpu`
  profile on machines without an NVIDIA runtime too, where `llm-runtime` cannot start. Jobs that
  arrive before the runtime is ready fail as `provider_unavailable`, which Processing retries.
- ⚠️ Ollama's API has no authentication. Its port is never published on every interface: on
  `127.0.0.1` by default, and in the two-host layout on the private-network address that
  `OLLAMA_ADDRESS` names. The private network must still let only the main host reach it (threat
  model R-13).
- ⚠️ The two-host layout needs two Compose settings, both the runtime's private-network address:
  `OLLAMA_ADDRESS` on the GPU host and `LLM_RUNTIME_URL` on the main host. Their defaults, the
  loopback and the Compose service name, serve a single host. `WHADIO_NOTES__LLM__BASE_URL` in
  `.env` does not set it: that is the address for a worker run on the host itself.

## Alternatives Considered

- **vLLM:** high throughput with batching and an OpenAI-compatible API, but it reserves a fixed share
  of GPU memory at start and holds it while idle, which leaves too little for the ASR worker on a
  12 GB GPU. It serves one model per process and loads it from Hugging Face weights.
- **llama.cpp server:** the engine Ollama builds on, light and fast, but it serves the model given at
  start, keeps it loaded, and leaves finding and downloading GGUF files to the operator. Ollama adds
  a model library, pulling by tag and unloading idle models.
- **Ollama's OpenAI-compatible endpoint (`/v1/chat/completions`):** portable to other servers, as
  ADR-004 intended, but it takes neither `num_ctx` nor `truncate` and `shift` per request, so the
  window is the server's default and an oversized transcript would be cut without notice.
- **Cloud providers only:** rejected in ADR-004, since transcripts would always leave the deployment
  (FR-022) and every self-hoster would need a paid account (NFR-016).
