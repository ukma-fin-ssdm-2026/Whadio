# ADR-003: Centralize Meeting Content Authorization in a Dedicated Access Policy Component

## Status
Accepted — 2026-09-27

## Context

Whadio stores meeting audio recordings, transcripts, and AI-generated notes. These artifacts contain sensitive personal discussions, team deliberations, and personally identifiable information (PII). The architecture must guarantee that meeting content is never exposed to unauthorized users, regardless of how or where the content is requested.

### Functional Pressures
- **Multiple egress paths for meeting content:** Meeting data leaves the system through four distinct consumers:
  1. *Web SPA:* Members browsing meetings, viewing transcripts, and playing audio (FR-027, FR-031).
  2. *MCP Server:* Personal AI assistants (Claude, Cursor) querying meetings using personal API keys (FR-043, FR-044).
  3. *Export Module:* Exporting transcripts and notes as Markdown or WebVTT files (FR-040–FR-042).
  4. *Processing Pipeline:* Assembling the "context set" (past transcripts from the same folder) to provide context for note generation (FR-019).
- **Compound access and restriction rules:**
  - Workspace members inherit access based on their role (`Owner`, `Moderator`, `Member`) (FR-006, FR-007).
  - A Moderator can restrict specific meetings to selected members, completely hiding them from all other members (FR-037).
  - External users can access a meeting via a read-only share link, once the share's creator approves their account, without gaining broader workspace access (FR-038).
  - Shared meetings can have speaker names redacted to anonymous labels (`Speaker 1`, `Speaker 2`) with audio playback withheld (FR-039).

### Non-Functional Pressures
- **Strict confidentiality (NFR-007, NFR-009):** Meeting recordings, transcripts, and notes must be accessible only to authenticated users who have explicit permission. Restricted meetings must be withheld across direct links, exports, and connected assistants.
- **Controlled sharing (NFR-008):** Recipients of shared meetings must not be able to forward, export, or download content beyond explicit permissions.
- **Performance (NFR-001):** Evaluating access rules must not prevent meeting lists from loading in under 2 seconds.

## Decision

Centralize all authorization logic for meeting content into a dedicated **Access Policy** component, mandating that all egress paths access meeting content exclusively through the **Meetings** module.

Specifically:
1. **Single Policy Decision Point (PDP):**
   - The `Access Policy` component is the single authority for determining whether an identity (workspace member, share recipient, or MCP key owner) may access a given meeting and what transformations (e.g. name redaction, audio withholding) must be applied.
2. **Single read path via Meetings:**
   - Direct database access to meeting recordings, transcripts, or notes by HTTP route handlers, export workers, or MCP handlers is strictly prohibited.
   - All reads must call the `Meetings` module, which unconditionally consults `Access Policy` before fetching or returning data.
3. **Pre-authorized context set assembly:**
   - When the `Processing` module prepares a note generation job, it requests the folder's context set through `Meetings`. `Access Policy` prunes any restricted meetings so that external LLMs or workers never receive unauthorized text.
4. **Pre-authorized worker payloads:**
   - Background workers (`asr-worker`, `notes-worker`) receive only pre-authorized job payloads from RabbitMQ; workers hold no user database credentials and perform no authorization logic.

## Consequences

- ✅ **Guaranteed authorization consistency (NFR-007, NFR-009):** Eliminates authorization drift; the Web UI, MCP server, export engine, and context assembler all enforce the exact same security rules without duplicating `if/else` checks.
- ✅ **Prevention of context-leakage in AI notes:** Because `Access Policy` filters the context set before job dispatch, sensitive or restricted transcripts in a folder cannot accidentally leak into notes generated for another meeting (FR-019, FR-037).
- ✅ **Single surface for security audits and testing:** Encapsulating all permission rules into one module centralizes authorization testing across roles, per-meeting restrictions, share links, and redactions in isolation.
- ✅ **Clear separation of concerns:** `Accounts & Workspaces` handles user authentication and role assignment; `Access Policy` handles content authorization; `Meetings` handles domain content.
- ⚠️ **Policy evaluation overhead on list queries:** Evaluating access rules for large paginated meeting lists requires translating policy rules into database query filters (e.g. SQL `WHERE` clauses) rather than filtering in-memory, to satisfy NFR-001.
- ⚠️ **High regression blast radius:** Because every content read passes through this single component, a bug or regression in `Access Policy` could inadvertently block legitimate access or expose content across all channels simultaneously.
- ❌ **Architectural indirection:** Developers cannot write direct or ad-hoc database queries to retrieve meeting data for new features; all data access must strictly navigate the `Meetings -> Access Policy` interface.
- ❌ **Coupled policy domain model:** Changes to sharing rules, role capabilities, or restriction scopes require modifying the centralized `Access Policy` module, increasing its coordination surface.

## Alternatives Considered

- **Decentralized controller-level checks:** Rejected because distributing manual authorization checks across Web API routes, MCP handlers, export workers, and pipeline jobs inevitably leads to human error, forgotten checks, and data leaks (violating NFR-009).
- **PostgreSQL Row-Level Security (RLS):** Rejected because Whadio's authorization logic involves application-level rules (revocable share grants to signed-in accounts, MCP personal keys, speaker name redactions, and cross-meeting context pruning) that are complex and brittle to maintain purely inside database policies.
- **Full Access Control Lists (ACLs) per object:** Rejected because Whadio's security model relies on a clear workspace role hierarchy and folder-level context scoping rather than individual file-level ACL management; a full ACL subsystem would add unnecessary administrative and database complexity.
