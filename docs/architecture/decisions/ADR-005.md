# ADR-005: Record Changes to Meeting Content and Access in a Dedicated Audit Module

## Status
Accepted — 2026-09-28

## Context

NFR-010 requires that 100% of the listed changes an account makes to meeting content or access create an audit record with the actor's account ID, the action type, the target ID and the timestamp, without storing transcript, note or recording content, and that the record survives the deletion of the meeting or workspace it refers to.

### Functional Pressures
- **Changes happen in three modules:** Meetings (creation, renames, moves, deletion, transcript edits, speaker renames, notes regeneration, capacity eviction), Access Policy (restriction, access grants, shares, share-request decisions) and Accounts & Workspaces (invitations, membership and role changes, workspace deletion, provider configuration, MCP keys).
- **Deletion removes its own evidence:** FR-036 deletes a meeting with its recording, transcript and notes, FR-008 deletes a whole workspace, and NFR-003 evicts the oldest meeting when the cap is exceeded. Any record of the actor kept on the deleted rows disappears with them.
- **Existing actor columns do not cover the changes:** the data model records creators where domain rules need them (`MEETING.created_by_user_id` decides who may delete under FR-036; `EXTERNAL_SHARE.created_by_user_id` decides who approves requests under FR-038). Renames, moves, restriction changes, share revocation, role changes, member removal and provider configuration overwrite or delete their rows and keep no actor.
- **Each module owns its tables** (high-level design, section 2), so a history shared by three modules needs an owner of its own. This adds an Audit module to the module list of [ADR-001](ADR-001.md).

### Non-Functional Pressures
- **Accountability (NFR-010):** every listed change is attributable to an account.
- **Repudiation (threat model R-10):** a user must not be able to deny a change to content or access.
- **Capacity eviction abuse (threat model R-16):** a Member who uploads junk meetings to evict colleagues' meetings must be traceable to the upload that triggered each eviction.
- **Minimal personal data (NFR-010):** the record must not carry content.

## Decision

Introduce an **Audit** module that owns one append-only `audit_event` table. Every change an account makes to meeting content or access writes an event in the same transaction as the change.

Specifically:
1. **Writer:** the module that performs the change writes the event through Audit's interface: Meetings, Access Policy or Accounts & Workspaces. Audit depends on no other module.
2. **Contents:** actor account ID, action type, workspace ID, meeting ID, the ID of the affected subject (revision, share, member, invitation or MCP key), and IDs or enum values in `details`. Never content, and never meeting or workspace names. The action values are listed in [data-model.md](../data-model.md#audit-actions).
3. **Survival:** `workspace_id` and `meeting_id` carry no foreign key, so the events outlive a deleted workspace or meeting.
4. **Every event has an actor.** For a capacity eviction, the actor is the account whose newly queued meeting triggered it. Notes regeneration is recorded when the new notes are saved, with the requester as the actor, so a failed run records nothing (FR-026). Changes the system makes on its own, such as Retention's deletion of recordings, have no actor and are not audited. Glossary changes are not audited either: they affect later transcriptions, not an existing meeting.
5. **Append-only:** the table is owned by the migration role, and the application's database role holds only `INSERT` and `SELECT` on it.
6. **Reader and retention:** no API or dashboard reads the log; the operator consults it in the database when investigating an incident. Events are kept for the lifetime of the deployment.

## Consequences

- ✅ **Evidence survives deletion (NFR-010):** "who deleted this meeting" or "who evicted it" can still be answered after the meeting, or its whole workspace, is gone.
- ✅ **One place to answer "what did account X do":** a single table instead of actor columns spread across many tables.
- ✅ **Existing events cannot be altered from the application:** without update or delete grants, neither a bug nor a compromised application process can rewrite history (threat model R-21). It can still skip or forge new events.
- ✅ **Minimal personal data:** IDs only, so the log holds no meeting content.
- ⚠️ **The same-transaction rule depends on every writing module following it**, so it is verified by an integration test per action type.
- ⚠️ **The action list grows with every new feature** that changes content or access.
- ❌ **A new component that three modules depend on.**
- ❌ **The log grows without limit and outlives deleted meetings.** Keeping it for the deployment's lifetime is acceptable because no requirement deletes accounts. Adding account deletion would require revisiting this, since `actor_user_id` references the account.
- ❌ **Nothing in the product reads it**, so its correctness is verified only by tests and by the operator.

## Alternatives Considered

- **Actor columns (`updated_by`, `deleted_by`) on every changed table:** Rejected because deletion erases the columns together with the rows (FR-036, FR-008, NFR-003), overwriting a column keeps only the last actor, and the evidence would be spread across many tables. The existing creator columns stay, because domain rules need them.
- **Soft-delete tombstones:** Rejected because every deletable table would need a tombstone, and every read path would have to filter them out, including the paths Access Policy guards.
- **A log inside Accounts & Workspaces:** Rejected for low cohesion: identity and workspace administration have nothing to do with transcript edits or notes regeneration.
- **Application logs:** Rejected because they are not transactional with the change, are rotated away, are mixed with operational noise, and risk leaking personal data or content.
