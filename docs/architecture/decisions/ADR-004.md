# ADR-004: Local-First LLM Architecture with Optional BYOK Provider Routing

## Status
Accepted — 2026-09-27

## Context

Whadio transforms raw meeting transcripts into structured notes (summaries with action items, detailed write-ups, interview notes). Generating high-quality notes in Ukrainian and mixed Ukrainian–English speech requires capable language models. The architecture must resolve the inherent tension between data privacy, summarization quality, and operational cost.

### Functional Pressures
- **Default zero-leak operation (FR-022):** Without an external provider configured, notes must be generated by the built-in local model, and no data or request may leave the system.
- **Owner-configured BYOK integration (FR-021):** A workspace Owner can connect an external LLM provider API key to achieve higher summarization quality. Workspace members must be informed that transcripts are sent to that provider.
- **Provider failure recovery (FR-023):** If a configured external provider fails (due to rate limits, authentication issues, or outages), the system must report the failure cause and offer or perform fallback generation using the built-in model.
- **Fixed prompt presets (FR-018):** Notes are generated using fixed named presets; users cannot view, edit, or enter custom prompts.

### Non-Functional Pressures
- **Strict data privacy (requirements.md Purpose, FR-022):** Meeting transcripts contain confidential deliberations and PII. Default note generation must execute entirely within Whadio's own infrastructure without sending transcripts to third-party LLM APIs.
- **Secret confidentiality (NFR-013):** Provider API keys carry financial liability and must be accessible strictly to the workspace Owner, never exposed to other workspace members or untrusted execution nodes.
- **Fault tolerance (NFR-015):** An external LLM API outage or quota exhaustion must not cause the entire service or note generation pipeline to collapse.
- **Self-hosting without external dependencies (NFR-016):** The open-source system must be deployable on documented hardware without mandating external cloud API accounts or paid commercial services.

## Decision

Implement a **local-first LLM note-generation architecture** using a self-hosted, OpenAI-compatible runtime by default, coupled with a workspace-level **Bring Your Own Key (BYOK)** provider abstraction layer and optional fallback to the built-in model.

Specifically:
1. **Built-in local runtime (`llm-runtime`):**
   - The deployment packages an off-the-shelf local inference server (e.g. `llama.cpp` server or `vLLM`) exposing a standardized OpenAI-compatible `/v1/chat/completions` API for open models (Gemma, Qwen).
   - All workspaces use this local model by default, ensuring zero external network egress.
2. **BYOK provider routing layer:**
   - The `notes-worker` includes a unified provider client supporting an explicit enum of commercial providers: Anthropic, OpenAI, and Google.
   - Provider selection and API keys are configured at the workspace level, stored encrypted in PostgreSQL, and managed exclusively by the workspace Owner.
3. **Secret confinement to the main host:**
   - External provider API keys are injected exclusively into the `notes-worker` running on the trusted main host.
   - Keys are never transmitted over the private network to the GPU host or stored in worker images.
4. **Resilience and failure recovery:**
   - If an external provider request fails (HTTP 429, 5xx, or network timeout), the meeting is shown as failed with the cause, and generation with the built-in model is offered (FR-023). Automatic fallback cannot be assumed because `llm-runtime` can be shut down if all workspaces use external providers.
5. **Fixed prompt templates:**
   - Prompts are assembled programmatically by the `notes-worker` using fixed template presets (summary, detailed, interview) combining the meeting transcript and authorized folder context. User-defined prompts are rejected by design.

## Consequences

- ✅ **Guaranteed privacy out of the box (requirements.md Purpose, FR-022):** Self-hosters, academic groups, and privacy-conscious organizations can deploy Whadio with absolute certainty that no meeting transcripts leave their infrastructure.
- ✅ **Quality escape hatch without ongoing service costs:** Teams needing frontier-model Ukrainian summarization can supply their own API keys, gaining state-of-the-art notes without Whadio incurring per-token infrastructure expenses.
- ✅ **Service resilience and fallback path (NFR-015, FR-023):** External commercial API outages, rate limits, or expired keys do not dead-end note generation; users are offered fallback generation using the built-in local model.
- ✅ **Protection against user-authored prompt injection (FR-018):** Enforcing fixed presets prevents users from submitting arbitrary system prompts or overriding note formats. (Note: indirect prompt injection via spoken meeting transcripts remains a risk to be handled at the prompt engineering and model level).
- ✅ **Secret isolation from GPU host:** External API keys remain confined to the secure main host and are never transmitted to the GPU worker node.
- ⚠️ **Provider key transit in message queue:** When a note job is dispatched, the workspace Owner's provider API key travels in the `NotesRequested` AMQP message payload (sequence diagram line 81) to `notes-worker`, temporarily residing in the durable RabbitMQ broker queue on the main host.
- ⚠️ **Output quality disparity:** Notes generated by smaller local models will exhibit noticeable differences in phrasing, depth, and Ukrainian language nuance compared to commercial frontier models; the UI must clearly attribute which model produced the current notes.
- ⚠️ **Context window constraints on local models:** Local models have tighter effective token limits than commercial APIs, requiring the backend to strictly prune and bound the folder context set during prompt assembly.
- ⚠️ **Provider client maintenance:** Supporting Anthropic, OpenAI, and Google simultaneously requires maintaining multiple API client libraries and mapping their divergent error schemas.
- ❌ **Compute resource consumption:** Running a local LLM runtime alongside ASR models increases memory and compute demands, requiring careful worker scheduling or CPU quantization fallbacks.
- ❌ **Multiple failure modes to support:** The system must handle both local runtime crashes (GPU OOM) and external network failures (HTTP 429 rate limits), increasing error-handling code paths.

## Alternatives Considered

- **Mandatory commercial LLM APIs (Cloud-only):** Rejected because requiring external API keys would break zero-configuration self-hosting (violating NFR-016) and force confidential transcripts outside the system boundary (violating requirements.md Purpose and FR-022).
- **Local LLM only (No BYOK option):** Rejected because current open-source local models running on consumer hardware cannot yet match frontier models in complex mixed-language Ukrainian–English summarization; removing BYOK deprives professional teams of a vital quality option.
- **User-defined custom prompts:** Rejected because allowing users to enter custom system prompts opens the application to prompt injection vulnerabilities, unpredictable output structures, and difficult supportability; fixed presets fully satisfy all defined user stories (FR-018).
