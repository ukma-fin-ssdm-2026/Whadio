# ADR-002: Separate the ML Pipeline onto a Dedicated GPU Host with Credential-Free Access

## Status
Accepted — 2026-09-27

## Context

Whadio delivers meeting recording, transcription, and summarization to users through a web application. The core machine learning tasks — speech recognition (ASR with Parakeet/Whisper), speaker diarization (pyannote), and local language model summarization (`llm-runtime`) — require intensive NVIDIA GPU compute. The system must decide how to partition and secure this compute relative to the user-facing web services.

### Cost and Hardware Pressures
- **GPU operational cost:** Cloud GPU instances represent the dominant ongoing financial cost (≈ $2/hour). To keep the service cost-effective and self-hostable, the reference production setup uses a team member's physical workstation equipped with an NVIDIA GPU, operating behind residential NAT.
- **Continuous web availability:** The main web application (Nginx, FastAPI web API, scheduler, PostgreSQL, RabbitMQ, and S3-compatible object storage) runs on an inexpensive, always-on Linux CPU virtual machine.
- **Decoupled host filesystems:** Because the backend services and GPU workloads run on physically separate machines, they cannot share a local filesystem or volume mount.

### Security and Privacy Pressures
- **Confidentiality and least privilege (NFR-007, NFR-009):** Meeting audio and transcripts contain sensitive personal and organizational data. 
- **Untrusted / perimeter execution environment:** Because the GPU machine resides on a residential network or dynamic secondary instance, it must be treated as a segregated, lower-trust security zone. If a worker container or the GPU host itself is compromised, an attacker must not obtain access to the wider database or other workspaces' stored recordings.

### Performance and Durability Pressures
- **Transcription SLA (NFR-002):** A 60-minute recording must be transcribed within 15 minutes in 90% of runs, necessitating dedicated GPU acceleration.
- **Component isolation and recoverability (NFR-014, NFR-015):** The GPU host can be powered off or rebooted without causing data loss or taking down the web API. Unprocessed jobs must wait safely on the main host.

## Decision

Deploy GPU-intensive ML workloads (`asr-worker` and `llm-runtime`) on a **dedicated GPU host** isolated from the main application host, granting **credential-free access** via ephemeral presigned S3 URLs and an encrypted private overlay network.

Specifically:
1. **Zero database credentials on the GPU host:**
   - The GPU host holds no PostgreSQL credentials or direct database connections.
   - All data required for transcription (audio reference, speaker timeline events, and workspace glossary terms) arrives directly inside the AMQP message payload (`TranscriptionRequested`) published by the backend.
2. **Credential-free audio access via presigned URLs:**
   - The `asr-worker` holds no permanent S3 access keys or secret credentials.
   - The backend `Processing` module generates a short-lived, read-only **presigned HTTPS URL** pointing to the specific meeting recording in object storage.
   - The worker fetches only the audio file authorized for that specific job, with the URL expiring shortly thereafter.
3. **Encrypted private tunnel without public ingress:**
   - The GPU host opens no public ports to the internet.
   - Network connectivity between the main host and the GPU host is established over an encrypted private overlay network (such as a WireGuard tunnel or a Tailscale/Headscale mesh), allowing reliable communication even with the GPU host located behind home NAT.
4. **Identical single-host compatibility (NFR-016):**
   - For single-machine local development and CPU-only testing, both Docker Compose profiles (`core` and `gpu`) run locally using the same AMQP contracts and URL fetching mechanisms.

## Consequences

- ✅ **Defense in depth and historical data protection:** Compromise of the GPU machine or native ML libraries yields zero direct database access, preventing extraction of user credentials, access tokens, workspace metadata, or historical transcripts.
- ✅ **Audio exposure bounded to in-flight jobs:** Worker access to audio is restricted to time-limited presigned URLs delivered in job messages; workers hold no permanent storage credentials.
- ✅ **Independent cost and lifecycle management:** The GPU host can be booted on demand, paused, or upgraded without interrupting web traffic or losing meetings stored on the main host.
- ✅ **No public attack surface on GPU host:** Operating behind an outbound-initiated private tunnel means the GPU machine requires no public IP, open firewall ports, or public TLS certificates.
- ✅ **Clean operational portability (NFR-016, NFR-017):** The application code remains completely agnostic of the physical deployment layout; single-host and two-host setups share identical worker logic.
- ⚠️ **Tunnel stability and NAT traversal:** If the private tunnel between the main host and the GPU machine drops, jobs accumulate in RabbitMQ until connectivity is restored.
- ⚠️ **Network dependency for audio transfer:** The GPU worker must download the entire audio recording over the private tunnel before starting ASR, adding network latency that directly depends on the home internet upload/download speed.
- ⚠️ **Cross-host HTTP call for LLM notes:** The `notes-worker` running on the main host calls `llm-runtime` on the GPU host over HTTP across the private network, introducing network latency into the summarization pipeline.
- ❌ **In-flight queue exposure and message tampering:** Because `asr-worker` holds broker credentials, a compromised GPU host could drain `transcription.requests` (accessing presigned URLs, timelines, and glossaries for pending in-flight jobs until the URLs expire) or publish forged `TranscriptReady` messages (Tampering).
- ❌ **Dual-host operational overhead:** Maintaining two physical environments, managing Docker Compose profiles across multiple machines, and troubleshooting overlay network tunnels increases administrative effort.
- ❌ **Network bandwidth consumption:** Audio recordings must be streamed over the private network from the main host's object storage to the GPU worker, adding network transfer time compared to a shared local disk.

## Alternatives Considered

- **Shared filesystem / Network File System (NFS):** Rejected because mounting a remote filesystem over residential internet and VPN tunnels is notoriously brittle, suffers from high latency, lacks fine-grained object-level expiry, and couples file permissions across distinct operating environments.
- **Direct database and storage credentials on GPU host:** Rejected because providing the GPU host with permanent PostgreSQL credentials and full S3 read/write keys violates the principle of least privilege; a security compromise on the GPU host would instantly expose all historical meetings and customer data.
- **Single co-located machine for all production workloads:** Rejected because running full-precision ASR, PyTorch, LLM runtime, PostgreSQL, RabbitMQ, and the web server on a single server would require continuously renting an expensive cloud GPU instance (≈ $2/hr) or hosting the production web application on an unreliable residential PC.
- **Commercial Cloud Speech APIs (Google Speech-to-Text, AWS Transcribe):** Rejected because transmitting meeting audio to third-party cloud APIs violates Whadio's privacy mandate (requirements.md Purpose: "processes audio only on its own servers") and introduces recurring per-minute operational costs.
