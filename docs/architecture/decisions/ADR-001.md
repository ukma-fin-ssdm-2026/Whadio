# ADR-001: Adopt a Modular Monolith with Broker-Driven Worker Processes

## Status
Accepted — 2026-09-27

## Context

Whadio is an open-source meeting recording and transcription service that delivers transcripts, speaker labels, and AI notes to users via a React Web SPA, a Chrome extension, and an MCP client. The system must define an architectural style that balances the web application's responsiveness, the resource demands of machine learning (ASR, diarization, and LLM summarization), and the operational constraints of the development team.

### Functional Pressures
- **Sequential multi-stage processing:** Meeting ingestion, speech recognition with diarization, note generation, and delivery are sequential stages where each stage consumes outputs and context from prior stages (FR-015, FR-016, FR-018, FR-019).
- **Concurrent user operations:** The web interface must allow users to manage workspaces, organize folders, edit transcripts, share meetings, and export files concurrently while long-running background processing takes place (FR-001–FR-008, FR-027–FR-042).
- **Scoped cross-meeting context:** Generating notes requires assembling transcripts of other meetings in the same folder while strictly excluding restricted meetings (FR-019, FR-037).
- **Transparent state reporting:** The processing state (`queued`, `processing`, `processed`, `failed`) must be continuously tracked and exposed to both users and the administrator dashboard without revealing sensitive meeting content (FR-014, FR-045).

### Non-Functional Pressures
- **Fault tolerance and component isolation (NFR-015):** A failure, crash, or out-of-memory (OOM) error in the speech recognition or note generation components must not degrade or bring down the web application. Unrelated functionality must remain accessible.
- **Recoverability and durability (NFR-014):** Ingested audio recordings and metadata must remain durably stored even if processing workers are temporarily offline or crash. Jobs must be retried or processed once workers recover.
- **Performance efficiency (NFR-001, NFR-002):** Web pages must load in under 2 seconds for 90% of requests. A 60-minute recording must be transcribed within 15 minutes in 90% of runs, requiring dedicated GPU inference without blocking web request threads.
- **Data privacy (requirements.md Purpose, FR-022):** Audio is processed only on Whadio's own servers and does not leave the infrastructure by default.
- **Access control and confidentiality (NFR-007, NFR-009):** Meeting content access must be strictly guarded across every path (web, MCP, export, context assembly).
- **Secret confidentiality (NFR-013):** External provider API keys carry financial liability and must remain strictly confidential to the workspace Owner, isolated within the trusted host environment.
- **Portability and installability (NFR-016, NFR-017):** The system must be deployable via Docker Compose with clear resource documentation, functioning seamlessly either on a single machine (self-hosted / development) or across two machines (main host + GPU host).
- **Resource and team constraints (Team Charter):** A team of 4 students working ≈ 22 person-hours/week over 11 weeks cannot afford the operational overhead, network orchestration, and distributed data consistency issues of microservices. Furthermore, GPU instances are the dominant financial cost and must be isolated so they can be managed or paused independently.

## Decision

Adopt a **modular monolith with broker-driven worker processes**, built from a single codebase and packaged into a single container image with four distinct runtime entry points communicating asynchronously via a RabbitMQ message broker.

Specifically:
1. **Single codebase, single container image, four entry points:**
   - `web`: Serves Web API (HTTPS/JSON), Capture API (chunked audio upload), and MCP Server (for AI assistants). Embeds session authentication and delegates content access to `Access Policy`.
   - `scheduler`: Manages periodic background jobs (audio retention cleanup, interrupted capture assembly, and re-publishing stale queued jobs).
   - `asr-worker`: Runs the transcription pipeline (audio normalization, Parakeet/Whisper speech recognition with glossary biasing, pyannote diarization, and speaker naming) on the GPU host.
   - `notes-worker`: Runs the notes pipeline on the main host, keeping external provider API keys confined to the trusted environment (NFR-013), constructing prompts from presets and authorized context sets, and dispatching to the local `llm-runtime` (or an external BYOK provider).
2. **Layered modular backend:**
   - The backend is organized into bounded modules (`Accounts & Workspaces`, `Meetings`, `Access Policy`, `Capture`, `Processing`, `Export`, `Notifications`, `Retention`, `Admin & Monitoring`). Each module defines an API, domain, and persistence layer, and owns its specific PostgreSQL tables.
3. **Asynchronous broker-driven orchestration:**
   - The backend `Processing` module orchestrates pipeline execution by publishing job commands (`TranscriptionRequested`, `NotesRequested`) and listening for worker results (`JobStarted`, `TranscriptReady`, `NotesReady`, `TranscriptionFailed`, `NotesFailed`) over RabbitMQ (AMQP). Workers operate as stateless consumers. Only `Processing` communicates directly with the broker.
4. **Architectural boundaries and delegated decisions:**
   - **Worker isolation:** Worker modules never import backend domain/persistence code or PostgreSQL models; they share only a lightweight job contracts library with the backend (enforced via CI import-linter). Credential-free audio access and worker isolation onto a dedicated GPU host are decided in [ADR-002](ADR-002.md).
   - **Centralized authorization:** Every read of meeting content must pass through `Meetings`, which delegates authorization logic to `Access Policy`, as decided in [ADR-003](ADR-003.md).

## Consequences

- ✅ **Process-level fault isolation (NFR-015):** Heavy ML inference runs in separate OS processes. An out-of-memory error or native crash in PyTorch or CUDA does not impact the web API or terminate active user sessions.
- ✅ **Job durability and backpressure (NFR-014):** RabbitMQ stores pending jobs durably on the main host. Workers consume one job at a time, providing natural backpressure that protects GPU memory from spikes. Ingested recordings remain safely stored while workers recover.
- ✅ **High web responsiveness (NFR-001):** The web server never blocks on long-running ML tasks; incoming audio chunks and user actions return immediate HTTP responses while processing occurs asynchronously.
- ✅ **Process and infrastructure flexibility (NFR-013):** Decoupling the ML workers from the web server enables different security profiles and deployment topologies. Running `notes-worker` on the main host keeps external provider keys within the trusted security perimeter (NFR-013).
- ✅ **Low operational overhead for small team:** A single codebase, unified Docker image, shared database, and shared CI pipeline eliminate the versioning, deployment, and data synchronization overhead of distributed microservices.
- ✅ **Flexible deployment topology (NFR-016, NFR-017):** Supports both single-host deployment (Docker Compose running all containers on one machine) and two-host deployment (CPU main host + GPU host connected via a private network like WireGuard/Tailscale) without code modifications.
- ⚠️ **Modular discipline required:** Because backend modules live in the same codebase and database, internal boundaries must be actively defended through automated linting (`import-linter` in CI) and rigorous code reviews to prevent architectural erosion.
- ⚠️ **Asynchronous user experience:** The web client cannot receive immediate completion; the SPA must handle asynchronous updates, intermediate processing states (`queued`, `processing`), and cases where transcripts are readable before notes are ready.
- ⚠️ **Orchestrator state management:** The `Processing` module must robustly handle timeouts, worker disconnections, and idempotency to prevent meetings from being permanently stuck in transient states.
- ❌ **Multi-container local development:** Developers cannot run a simple single-script environment; local testing requires orchestrating several containers (`web`, `scheduler`, `workers`, `rabbitmq`, `postgres`, `object-storage`).
- ❌ **Cross-process distributed debugging:** Troubleshooting a failed meeting processing run requires correlating events across web logs, RabbitMQ queue states, and worker container outputs rather than inspecting a single monolithic stack trace.
- ❌ **Inter-host private networking complexity:** In the reference two-host production setup, configuring and securing the private overlay network between the main host and the GPU host behind NAT introduces additional networking maintenance.

## Alternatives Considered

- **Microservices (one service per capability):** Rejected because a 4-person team in a single repository cannot justify the operational overhead of distributed data stores, distributed transactions, and multiple CI/CD pipelines.
- **Single-process monolith (models in web process):** Rejected because a GPU out-of-memory error or ML crash would bring down the entire web service (violating NFR-015), and the web host would require an expensive, always-on GPU.
- **Pure event-driven choreography:** Rejected because assembling folder context sets, selecting presets, and enforcing access rules (FR-019, FR-037) requires centralized backend orchestration rather than direct worker-to-worker event consumption.

*(Detailed evaluations of queue implementations and internal worker splits are documented in [high-level-design.md](../high-level-design.md#alternatives-considered). Worker credential isolation is decided in [ADR-002](ADR-002.md), and centralized authorization is decided in [ADR-003](ADR-003.md).)*
