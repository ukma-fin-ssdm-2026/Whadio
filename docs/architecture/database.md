# Database implementation

PostgreSQL is the source of truth. SQLAlchemy models live in each table owner's `models.py`;
Alembic loads them at its composition root in `migrations/env.py`. Repositories and business
services are the next implementation step; the HTTP API still uses demo fixtures.

## Running migrations

Install dependencies with `uv sync`, copy `.env.example` to `.env`, and start the infrastructure
with `uv run task infra:up`. From the repository root, run:

```sh
uv run whadio db-upgrade
uv run alembic current
uv run alembic check
```

`WHADIO_DB_HOST`, `WHADIO_DB_PORT` and `WHADIO_DB_NAME` select the database. The connection port
must match `POSTGRES_PORT` when that Compose port is overridden. Migrations use `whadio_owner`
and `WHADIO_DB_OWNER_PASSWORD`; application transactions use `whadio_app` and
`WHADIO_DB_APP_PASSWORD`. The runtime settings do not require or expose the owner password.
Neither connection string is stored in `alembic.ini`.

To review SQL without connecting or providing credentials:

```sh
uv run alembic upgrade head --sql
```

Use migrations to build a database, not `Base.metadata.create_all()`: revision 0002
installs database triggers and restricts Audit privileges; revisions 0003 and 0004 close the
original-content and folder-deletion gaps. Migration history is frozen;
future changes belong in new revisions. Review autogenerated revisions, especially cycles,
triggers, privileges and data transformations, which Alembic cannot infer completely.

## Ownership and transactions

| Module | Tables |
| --- | --- |
| Accounts | user, workspace, workspace_membership, invitation, pending_registration, password_reset, session, llm_provider_config, mcp_key |
| Meetings | folder, meeting, transcript, transcript_revision, speaker, transcript_segment, glossary_term, note, note_context_meeting |
| Access Policy | meeting_access_grant, external_share, share_access_request |
| Capture | capture_session, capture_chunk |
| Processing | processing_job |
| Audit | audit_event |

These are the 25 entities in the ER diagram. Retention owns no table in this initial schema;
it will request meeting retention state through Meetings. Foreign keys refer to table names,
so models do not import another module's models.

The runtime constructs `Database` and closes it on shutdown. A use case enters
`database.transaction()` and passes its session to every participating repository, including
Audit. Repositories must not commit independently. Leaving the context commits on success and
rolls back on an exception. A session belongs to one use case and is not shared across concurrent
tasks. UUIDs are generated by the application; timestamps are timezone-aware PostgreSQL values.

## Integrity boundaries

Foreign keys, checks and indexes enforce valid enum values, case-insensitive email uniqueness,
single-use token lookup uniqueness, one membership per user/workspace, one pending invitation per
address/workspace, chunk sequence uniqueness, and transcript/speaker reference consistency.
Folder names are unique per workspace ignoring case, including the default folder. Revision 0004
fails if existing names conflict; resolve duplicates explicitly before upgrading rather than
having the migration rename user data.

Deferred constraint triggers enforce exactly one Owner and default folder per workspace, a
nonempty member grant list for restricted meetings, and one original revision per transcript.
Create related rows in one transaction. Removing a member must also remove their grants and
resolve any meeting that would otherwise have an empty restricted list in that transaction.
Changing a folder or meeting to a different workspace is rejected. Original revisions, segments
and speaker labels cannot be updated or deleted independently of their containing transcript.
Create an original revision, its speakers and its segments in one transaction. Revision 0003
stamps `transcript_revision.initialization_xid` with PostgreSQL's top-level transaction ID;
inserts and moves into that original are accepted only within that transaction, including
savepoints. The trigger overrides caller-supplied IDs. Existing revisions are sealed during
upgrade. Edited revisions cannot be relabelled as originals.

Deleting a meeting cascades to its dependent content and access rows. Context references in other
notes become null while their name snapshots remain. Workspace deletion cascades through folders
and meetings. Deleting a nondefault folder moves its meetings to the workspace's default folder
in the same transaction, preserving all content and access rows. The default folder cannot be
deleted while its workspace exists. Workspace deletion bypasses this move and cascades normally.
The application still has to implement permission checks, deleting storage objects, and writing
one `meeting_moved` audit event per moved meeting with the requesting actor. The trigger is a
data-preservation safeguard, not a complete folder-deletion use case.

Audit events have no workspace or meeting foreign key and survive those deletions. The application
can only insert and select audit rows. Audit's future writer must validate action-specific details
as IDs and enum values and reject content or names. The actor references an existing account;
account deletion is outside the current requirements.

Business rules such as invitation throttling, registration completion, external-share approval,
authorization, and notification delivery remain service responsibilities. Database constraints
are not a replacement for Access Policy. Shares store `include_recording = false`, matching the
API's transcript-and-notes-only contract.

The recording retention interval was confirmed on 2026-10-10 as **90 days**, with warnings
**7 days before deletion**, rather than three calendar months.
This change records those decisions; it does not implement the Retention scheduler or email delivery.

## Verification

The database tests are marked `slow`. Point `WHADIO_TEST_DATABASE_URL` at a migrated, disposable
database using the application role, then run `uv run task test`. The fixture rolls every test
transaction back. Original-sealing tests commit their initial fixture to test a later transaction,
then delete only their own workspace and account during cleanup. Without this variable,
PostgreSQL tests are explicitly skipped; fast tests still run. Do not treat a skipped database
suite as migration verification.

Test fresh upgrades, downgrade/upgrade cycles on disposable databases, `alembic check`, privilege
denials, invalid relationships, deferred invariants, cascades and audit rollback. A downgrade
removes schema and data; never run it on a database whose contents must be preserved.
