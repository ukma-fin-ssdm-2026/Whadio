# Whadio Threat Model

This document applies STRIDE to the production deployment diagram in [`uml/deployment-diagram.puml`](uml/deployment-diagram.puml). The diagram marks trust boundary crossings with `[TB-1]` through `[TB-8]`.

## Scope

The model covers the two-host production layout: user clients, Google Meet, nginx, web, scheduler, notes-worker, RabbitMQ, PostgreSQL, object storage, GPU host, asr-worker, local LLM runtime, external LLM providers, and SMTP relay. In the single-host profile both Compose profiles run on one machine, so `TB-6` disappears; the remaining boundaries still apply.

The most sensitive assets are password hashes, meeting recordings and capture chunks, transcripts, speaker labels, notes, note context records, glossary terms, consent confirmations, workspace membership and roles, invitation emails, registration, invitation, password-reset and session tokens, external share tokens, share access requests, MCP keys, provider API keys, processing metadata, and audit events.

## Trust Boundaries

| ID | Boundary | Data crossing it | Why trust changes |
| --- | --- | --- | --- |
| `TB-1` | Browser or MCP client to nginx | Sessions, extension tokens, uploads, API calls, MCP requests, meeting content | User-controlled devices and external clients call the public Whadio entry point. |
| `TB-2` | Extension to Google Meet page | Participant names and active-speaker events | The extension reads a third-party page outside Whadio control. |
| `TB-3` | nginx to web container | Authenticated HTTP requests | Public traffic becomes internal application traffic after TLS termination. |
| `TB-4` | Web/scheduler to PostgreSQL and object storage | Metadata, recordings, chunks, transcripts, notes, keys, shares | Application code crosses into persistent storage. |
| `TB-5` | Web/scheduler/workers to RabbitMQ | Processing jobs, transcripts, context sets, provider-key material, status events | Components trust durable broker messages to start work or update state. |
| `TB-6` | Main host to lower-trust GPU host | AMQP traffic, presigned audio URLs, local LLM requests | Processing crosses a private mesh to a team member's GPU workstation treated as a lower-trust zone. |
| `TB-7` | Notes worker to external LLM provider | Transcript and context text, BYOK credential use | Meeting content leaves Whadio only when configured by a workspace Owner. |
| `TB-8` | Web container to SMTP relay | Notification metadata, email addresses, and single-use registration, invitation and password-reset links | Whadio depends on an external mail service. |

## Identified Risks

| ID | Component or boundary | STRIDE category | Scenario | Rating | Requirements | Planned countermeasure or accepted decision |
| --- | --- | --- | --- | --- | --- | --- |
| `R-01` | `TB-1` browser/MCP/extension client to nginx | Spoofing | An attacker steals a browser session, extension capture token, or MCP key and accesses meetings as the victim. | High | `FR-003`, `FR-004`, `FR-043`, `FR-044`, `FR-048`, `NFR-012` | Use secure, HttpOnly, SameSite session cookies; keep sessions and extension tokens server-side as token hashes, deleted on sign-out and when the password is reset; store extension tokens only in extension storage, scope them to Capture API, expire them quickly, and revoke them on sign-out; hash MCP keys, show them once, support revocation, rate-limit failed authentication, and authenticate every content endpoint. |
| `R-02` | Web backend authorization | Elevation of privilege | A Member calls an API endpoint intended for Moderator, Owner, or Administrator actions, such as restricting a meeting, managing members, configuring a provider key, or reading monitoring data. | High | `FR-007`, `FR-021`, `FR-037`, `FR-045`, `NFR-013`, `ADR-003` | Enforce role checks server-side through Access Policy or Accounts & Workspaces; cover content and administration endpoints with authorization tests; ignore client-side role state for decisions. |
| `R-03` | `TB-4` app to PostgreSQL/object storage | Information disclosure | A bug or overly broad presigned URL exposes a recording, capture chunk, transcript, or note to a user without meeting access. | High | `NFR-007`, `NFR-009`, `ADR-002`, `ADR-003` | Keep object storage private; issue short-lived presigned URLs only after access checks; never expose raw storage paths; use unguessable object keys; log access decisions without logging content. |
| `R-04` | Transcript revision and speaker labels | Tampering | Edited transcript text or renamed speaker labels overwrite the original record, making changed content appear original. | High | `FR-028`, `NFR-011` | Store immutable original revisions; save text edits and speaker-label changes as edited revisions; display and export an edited marker; enforce that current revisions belong to the same transcript. |
| `R-05` | `TB-7` external LLM provider | Information disclosure | When an Owner configures BYOK, transcript and folder-context text are sent to a third-party provider and may leave Whadio's privacy boundary. | High | `FR-021`, `FR-022`, `NFR-013`, `ADR-004` | Make BYOK opt-in and Owner-only; clearly show when provider mode is active; send only required context; store provider keys encrypted. Accepted: this disclosure is a deliberate Owner choice. |
| `R-06` | RabbitMQ and processing jobs | Tampering | A forged or replayed queue message marks processing as successful, attaches output to the wrong meeting, or starts processing with a stale presigned URL. | Medium | `FR-014`, `NFR-014`, `NFR-015`, `ADR-002` | Authenticate broker connections; isolate queues on the private network; include meeting/job IDs and expected state transitions; reject stale or duplicate job events; keep processing updates idempotent. |
| `R-07` | Upload and processing pipeline | Denial of service | A user uploads many large files or repeatedly regenerates notes, exhausting disk, queue capacity, CPU, GPU, or LLM runtime. | High | `FR-013`, `FR-025`, `NFR-002`, `NFR-015` | Enforce file size and duration limits; cap concurrent jobs; rate-limit uploads and note regeneration; show queue backpressure in monitoring; keep unrelated web features available. |
| `R-08` | `TB-2` extension to Google Meet page | Tampering | Google Meet DOM changes or malicious page manipulation causes wrong speaker names or active-speaker events to be stored. | Medium | `FR-016`, `FR-017`, `FR-028` | Treat Meet-derived names and speaker events as untrusted hints; allow speaker-label correction through edited revisions; fall back to generic Speaker N labels when extraction is unreliable; never use DOM labels for authorization. Accepted: there is no official Meet API in scope. |
| `R-09` | External share links and access requests | Information disclosure | A share token leaks or a recipient forwards a link; an unintended signed-in account requests access or tries to reuse an approved link. | Medium | `FR-038`, `FR-039`, `NFR-008`, `ADR-003` | Opening the link only creates an access request and returns no content; the share is bound to the one account its creator approves, and any other account that opens it sees no content; show the requesting account's name and email so the creator can recognise it, where the email was proven by an opened link or taken from an invitation (`NFR-018`), and never let a share link create an account (`FR-047`); store only token hashes; allow revocation; keep shares read-only and remove recording from redacted shares; audit share creation, revocation, approvals and declines (`ADR-005`). |
| `R-10` | Consent confirmation and audit trail | Repudiation | A user denies confirming participant consent, editing a transcript, renaming speakers, restricting a meeting, creating a share, approving or declining a share access request, changing membership, or configuring an external provider. | Medium | `FR-002`, `FR-009`, `FR-038`, `NFR-010`, `ADR-005` | Store `consent_confirmed_at` and `consent_confirmed_by_user_id` for extension recordings; for uploads rely on the Terms acceptance recorded when the account was created (`USER.terms_accepted_at`); record every other content and access change as an append-only Audit event with the actor, action type, target IDs and timestamp, written in the same transaction as the change and kept after the meeting or workspace is deleted. Accepted: Retention's deletion of recordings and the assembly of interrupted captures are system actions with no actor; `MEETING.recording_deleted_at` and `CAPTURE_SESSION.status` record that they happened. |
| `R-11` | `TB-8` SMTP relay | Information disclosure | Notification emails reveal meeting titles, workspace names, processing failures, or links to unintended recipients. | Low | `FR-024`, `FR-038`, `FR-046`, `NFR-007` | Send notification metadata only, never transcript/note/recording content; send only to addresses proven by an opened link or taken from an invitation (`NFR-018`); use STARTTLS; keep links behind sign-in and access checks. |
| `R-12` | Lower-trust GPU host and presigned URLs | Elevation of privilege | A compromised GPU host reuses presigned URLs, drains `transcription.requests`, or obtains broader object-storage/database access than needed. | High | `NFR-007`, `NFR-009`, `ADR-002` | Keep GPU host without public ports or database credentials; use short-lived read-only presigned URLs scoped to one object; rotate credentials; monitor unusual object access. Accepted residual risk from ADR-002: a compromised GPU host can access in-flight transcription jobs until URLs expire. |
| `R-13` | Private mesh between main and GPU hosts | Spoofing | Any device on the mesh reaches RabbitMQ, object storage, or `llm-runtime`, impersonating a worker or runtime endpoint. | High | `NFR-007`, `NFR-009`, `ADR-002`, `ADR-004` | Configure mesh ACLs so only the GPU host can reach broker/storage ports needed by `asr-worker`, and only the main-host `notes-worker` can reach `llm-runtime`; monitor unexpected mesh peers and deny all other east-west traffic. |
| `R-14` | `TB-5` RabbitMQ notes jobs | Information disclosure | `NotesRequested` messages persist transcripts, context sets, and the Owner's provider key material in the durable broker queue. | High | `FR-021`, `FR-022`, `NFR-013`, `ADR-004` | Encrypt provider keys inside payloads for the notes-worker, keep per-queue broker permissions so `asr-worker` cannot read `notes.requests`, and avoid logging message bodies. |
| `R-15` | Notes-worker, local LLM runtime, MCP output | Tampering | A participant speaks prompt-injection text that enters the transcript, notes prompt, future folder context, or MCP responses and tries to change model behavior or trigger actions. | Medium | `FR-018`, `FR-019`, `FR-043`, `FR-044`, `ADR-004` | Keep fixed presets; mark transcript/context as untrusted data in prompts; never let model output trigger actions; bound context sets; show model attribution. |
| `R-16` | Hosted meeting capacity eviction | Denial of service | A Member queues enough junk meetings to hit the Owner's cap, causing the Owner's earliest meetings, possibly in other workspaces, to be deleted under `NFR-003`. | Medium | `NFR-003`, `NFR-010`, `FR-036`, `ADR-005` | Rate-limit uploads; count only meetings queued for processing, so an abandoned capture evicts nothing; notify the triggering member and the evicted meeting's creator, naming the meeting only to a recipient who could read it; record each eviction as an audit event whose actor is the triggering account. Accepted: a meeting queued in one of the Owner's workspaces can evict a meeting in another, including one the triggering Member cannot read, because a per-workspace cap could be bypassed by creating more workspaces, and evicting only within the arriving workspace would leave a new workspace of an Owner at the cap holding a single meeting. |
| `R-17` | Administrator dashboard and failure causes | Information disclosure | The dashboard shows processing failures "with their causes"; raw exception messages may contain transcript snippets, file names, provider responses, or object keys visible to an Administrator. | Medium | `FR-045`, `NFR-007`, `NFR-010` | Store failure causes as bounded error codes plus sanitized details; keep raw exceptions out of the database and dashboard; allow correlation IDs for server logs with restricted operator access. |
| `R-18` | Single-main-host deployment | Denial of service | The main host fails, making web, storage, database, broker, and processing unavailable. | Medium | Project scope, `NFR-015` | Accepted: the semester scope explicitly has no uptime guarantee. Fault isolation still keeps web features available when workers fail, but a main-host outage is outside this version's availability target. |
| `R-19` | — | — | Withdrawn: merged into `R-08`, which covers the same Google Meet DOM dependency. | — | — | — |
| `R-20` | Local LLM runtime on lower-trust GPU host | Information disclosure | Default local notes send every transcript and folder context set to `llm-runtime` on the lower-trust GPU workstation, exposing historical transcript text to that host. | High | `FR-019`, `FR-022`, `NFR-007`, `ADR-002`, `ADR-004` | Accepted for the reference deployment: `llm-runtime` is part of Whadio's own infrastructure, but the GPU host is lower trust. Mitigate with mesh ACLs, no database credentials, no transcript persistence on the GPU host, disabled prompt logging, and documented operator trust assumptions. |
| `R-21` | Audit log in PostgreSQL | Tampering | An application bug or a compromised `web` or `scheduler` process updates or deletes audit events to hide who changed or deleted a meeting. | Medium | `NFR-010`, `ADR-005` | The audit table is owned by the migration role, and the application's database role holds only `INSERT` and `SELECT` on it, so existing events cannot be altered from the application; the application has no update or delete path for it. Accepted: a compromised application process can still skip or forge new events, and an operator with the migration role or superuser rights can rewrite existing ones. |
| `R-22` | Audit log in PostgreSQL | Information disclosure | The audit log maps people to their actions on meetings, including accounts outside the workspace that requested a share, and outlives the meetings it describes. | Medium | `NFR-010`, `ADR-005` | Store IDs and enum values only, never content or meeting and workspace names; expose no API or dashboard view of the log, so only the operator reads it from the database. Accepted: events are kept for the lifetime of the deployment, since no requirement deletes accounts. |
| `R-23` | Registration and invitations | Spoofing | An attacker registers someone else's email address to take an invitation addressed to it, pose as its owner in a share access request, or hold the address so its owner cannot register. | High | `FR-001`, `FR-006`, `FR-038`, `FR-047`, `FR-049`, `NFR-018` | Create an account only from an opened link sent to its address, from an invitation for that address, or from a link the operator issued for it; ask for the password only after the link is opened, so whoever registers first cannot set it; accept an invitation only from an account with the invited address. Open registration without verification is not offered. Accepted: accounts created through invitations in `invite-only` mode or from operator-issued links keep addresses vouched for by the invitation's creator or the operator, not proven, including after the instance switches to `verified`. |
| `R-24` | Registration, password-reset and invitation forms, `TB-8` | Denial of service | A script registers accounts in bulk, or uses the registration, reset and invitation forms to flood strangers' inboxes and damage the relay's sending reputation. | Medium | `FR-001`, `FR-006`, `FR-048`, `NFR-018` | Rate-limit both forms per IP in nginx; send at most one registration or reset email per address per 20 minutes, and let a request inside that window change nothing, so it cannot invalidate a link already sent; email an address at most one invitation to the same workspace a day, cancelled ones included, and let an account invite at most 20 addresses a day; a pending registration creates no account, workspace or audit event and is deleted when its link expires; send nothing for a reset requested for an unknown address. Accepted: email aliases and catch-all domains give one person many verified addresses, so verification raises the cost of bulk accounts but does not prevent it. |
| `R-25` | Registration, invitation and password-reset links | Spoofing | A link is read in a compromised mailbox, or a forwarded invitation link lets someone other than the invited person join under the invited address. | Medium | `FR-001`, `FR-006`, `FR-048`, `NFR-018` | Store only token hashes; make every link single-use and short-lived (24 hours, 7 days, 1 hour); carry tokens in the URL fragment and request bodies, never in paths or query strings; end every session and extension token when a password is reset. Accepted: whoever controls an inbox controls account creation and password reset for its address. |
| `R-26` | Registration, password reset and sign-in | Information disclosure | Responses reveal whether an email address has an account, exposing who uses Whadio. | Low | `FR-001`, `FR-003`, `FR-048`, `NFR-018` | Return identical responses for addresses with and without an account; tell the owner of a registered address by email instead of in the response; deny a failed sign-in without saying which credential was wrong. Accepted: email is sent within the request, so response timing can still differ between known and unknown addresses; and in `invite-only` mode a Moderator who opens their own invitation link learns whether the address has an account. |
| `R-27` | Invitations | Elevation of privilege | A Moderator creates invitations for addresses they control, is then removed or made a Member, and redeems the invitations to regain access to the workspace. | Medium | `FR-006`, `FR-007` | Accept an invitation only while its creator is still a Moderator or the Owner of the workspace, checked when it is accepted; let Moderators list and cancel pending invitations; expire invitations after 7 days and delete them then. |

## Design Constraints Derived From This Model

- All meeting content paths, including web UI, direct links, shares, exports generated on request, and MCP, must call the same server-side access policy (`NFR-007`, `NFR-009`, `ADR-003`).
- Credentials and tokens must be stored only as hashes or encrypted secrets, never as plaintext (`NFR-012`, `NFR-013`).
- Recording and chunk object access must be mediated by short-lived, access-checked URLs (`NFR-007`, `NFR-009`, `ADR-002`).
- Processing and note-generation jobs must be authenticated, idempotent, and tied to explicit meeting/job state (`NFR-014`, `NFR-015`).
- Audit records are required for meeting creation, renames, moves and deletions (including eviction), transcript edits, speaker-label changes, notes regeneration, access changes, shares, share request decisions, membership changes, workspace deletion, provider configuration, and MCP keys (`NFR-010`, `ADR-005`). Consent confirmations are stored on the meeting itself (`FR-009`).
- No account may exist whose email address was neither proven by an opened link nor taken from an invitation or from a link the operator issued for it (`NFR-018`).
- Single-use tokens travel only in URL fragments and request bodies, never in paths or query strings, so they stay out of nginx logs and `Referer` headers.
- Logs, monitoring, and administrator dashboard views must avoid recordings, transcript text, notes, raw keys, raw share, registration, invitation, password-reset and session tokens, provider credentials, and raw exception messages (`FR-045`, `NFR-007`, `NFR-010`).

## Private telemetry receiver constraints

Collectors publish operational measurements with source-scoped bearer credentials over HTTPS or
an encrypted private network. The receiver stores only SHA-256 token hashes in configuration,
limits sources and payload sizes, validates metric scope/ranges/timestamps, and rejects replayed
or out-of-order observations. Host credentials cannot publish runtime activity; a runtime
credential is pinned to ASR or notes. Deploy a private proxy ACL for the ingress route; do not
expose the GPU host or grant it database/storage credentials. Rotate source credentials after a
suspected compromise. Accepted residual risk: a compromised source can falsify its own bounded
measurements until its credential is revoked. Telemetry never controls job state or authorization.
Last-good samples expire and unknown values are not presented as zero. Collection failure must
not stop workers or unrelated content APIs.
